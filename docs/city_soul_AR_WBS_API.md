# 城市靈魂 AR 遊戲 — WBS 與 API 切分（腦袋／身體／臉）

## 0. 邊界決策（v2：降低耦合／減少延遲版本）

| # | 問題 | 決策 |
|---|---|---|
| 1 | 「當日情境」內容生成 vs 排程/分發 | **拆分**：內容生成邏輯算腦袋；**排程觸發＋快取＋對外 `/daily-event` API 算身體** |
| 2 | 口型同步(viseme)時間軸誰算 | **腦袋**：呼叫 Google Cloud TTS 時一併取得時間標記，跟音檔一起交給臉；臉只負責播放，不做音訊分析 |
| 3 | 共鳴值解鎖內容 | **身體判定達標 → 腦袋生成敘事內容**（沿用 `/quests/{questId}/complete` 的既有模式） |
| 4 | 記憶資料庫 schema owner | **拆分**：結構化欄位（任務進度、共鳴值數值）算**身體自己的資料表**；語意化欄位（對話摘要向量）算**腦袋的 pgvector 表**；兩者用 `player_id` 關聯，不合併成一張表 |

> ✅ **這個版本比 v1 耦合更低的原因：**
> - 身體的任務進度／共鳴值是**自己的資料表，自己讀寫**，不需要呼叫腦袋的任何介面，Profile 頁面查詢是純身體內部的 DB 查詢，延遲最低。
> - 腦袋只在「真的需要生成內容」時才被呼叫（例如共鳴值解鎖要生成故事、當日情境要生成敘事文本），這是唯一無法避免的耦合——**因為只有腦袋能呼叫 LLM**，這個呼叫本身就是必要的，不是架構設計造成的多餘延遲。
> - 當日情境的**排程觸發、快取、對外 serve** 這幾件事本質是基礎設施職責（Cloud Scheduler + 快取層），跟身體其他工作包（訊號推播、遊戲介面）性質更接近，讓身體負責可以共用同一套排程/快取基礎設施。
> - 唯一的跨模組資料關聯只剩下 `player_id` 這個外鍵——身體的結構化表跟腦袋的語意向量表用它對應，不需要共用 schema、不需要互相唯讀存取對方的表。

## 1. 最終模組歸位

### 🧠 腦袋（LLM／RAG／Memory）

- Vertex AI 單一快速模型串接與失敗回退策略
- Prompt 組裝引擎（人格卡 + 當日情境 + 記憶片段）
- 人格卡解析與版本管理（人工審核過的定義載入）
- 角色安全邊界檢查（自由輸入的安全過濾）
- 史實邊界規則注入（區分史實／傳說／想像）
- 短期記憶（Redis）存取層
- 長期記憶（pgvector）語意檢索與寫入（含 schema）
- 記憶摘要 nightly batch job
- **當日情境「內容生成邏輯」**（決策1：只做內容生成，不管排程/分發）
- TTS 串接＋**viseme 時間軸產出**（決策2）
- 共鳴值解鎖敘事生成（決策3，接收身體傳入的階段參數）

### 🦾 身體（互動／任務／遊戲介面／行銷）

- GPS／Fused Location 定位模組
- 在場驗證與召喚半徑判定
- 防作弊（mock location 偵測、移動速度合理性、伺服器端二次驗證）
- 任務狀態機判定邏輯**＋自己的任務進度資料表**（決策4：讀寫都是身體自己的）
- 共鳴值判定邏輯**＋自己的共鳴值資料表**（決策4：讀寫都是身體自己的）
- 匿名玩家身分系統／帳號升級綁定
- 遊戲介面 UI：地圖／召喚點／任務列表／Profile／引導提問元件
- **當日情境排程觸發＋快取＋對外 `/daily-event` API**（決策1）
- 訊號推播（低頻通知邏輯、訂閱管理）
- 紀念照片（裝置本地保存、分享）
- 行銷／社群分享功能

### 🎭 臉（動畫／2.5D／口型）

- 角色美術造型設計（Character Creator 產線）
- 精靈圖／序列幀烘焙管線
- Rive/Lottie 動畫實作（idle、揮手、轉身、撐傘、服裝與光影切層）
- 相機疊圖渲染（Flutter 相機畫面 + Avatar 疊層）
- 口型同步播放器（**播放**腦袋給的 viseme 時間軸，不做分析）
- 素材版本管理與上傳（Cloud Storage + CDN）
- App 端素材下載與快取邏輯

## 3. API 清單

### 對外 API（Flutter ↔ 後端）

| Method | Path | 所屬模組 | 說明 |
|---|---|---|---|
| POST | `/api/v1/summon` | 身體 | GPS 送出，觸發在場驗證；驗證通過後核發綁定單一玩家與該靈魂、有效 15 分鐘的相遇憑證 |
| GET | `/api/v1/spirits/{placeId}` | 身體 | 地標基本資料、召喚點座標 |
| POST | `/api/v1/spirits/{placeId}/dialogue` | 腦袋 | 必須帶有效相遇憑證；對話輸入 → LLM 回應 + TTS 音檔 + viseme 時間軸 |
| GET | `/api/v1/spirits/{placeId}/daily-event` | 身體 | 讀取當日情境（決策1：排程/快取/serve 都是身體，內容來自腦袋 B9 內部呼叫） |
| GET | `/api/v1/quests/daily` | 身體 | 每日任務列表 |
| POST | `/api/v1/quests/{questId}/complete` | 身體→腦袋 | 身體判定完成，**寫入自己的任務進度表**＋呼叫腦袋生成敘事包裝回傳 |
| POST | `/api/v1/resonance/{spiritId}/check` | 身體→腦袋 | 身體判定共鳴值達標，**寫入自己的共鳴值表**＋呼叫腦袋生成解鎖故事回傳 |
| GET | `/api/v1/players/me/memory-summary` | 身體 | Profile 頁面讀取共鳴值/任務進度，直查身體自己的資料表（決策4） |
| GET | `/api/v1/assets/{avatarId}` | 臉 | Avatar 素材下載 URL（經 CDN） |

### 內部介面（模組間，不對 Flutter 開放）

| 介面 | 呼叫方 → 被呼叫方 | 說明 |
|---|---|---|
| `daily_event.generate_content(placeId, date)` | 身體 → 腦袋 | S10 排程觸發時呼叫，取得當日情境內容後由身體快取並 serve |
| `narrative.generate_unlock_story(player_id, spirit_id, stage)` | 身體 → 腦袋 | 共鳴值解鎖敘事生成，身體判定達標＋寫完自己的表後呼叫 |
| `narrative.generate_quest_wrapper(player_id, quest_id)` | 身體 → 腦袋 | 任務完成敘事包裝，身體判定完成＋寫完自己的表後呼叫 |
| `tts.synthesize(text) → (audio, viseme_timeline)` | 腦袋 → 臉（經 dialogue API 回應一併帶出，非獨立呼叫） | 口型資料交付 |

> 這個版本的內部介面只剩「需要生成內容」的呼叫（都是身體主動呼叫腦袋要一段文字/故事），沒有任何「純資料讀寫」的跨模組呼叫——這是耦合最低、延遲最小的切法。腦袋、身體兩個模組理論上可以完全獨立測試（腦袋的介面用假的 player_id/stage 參數就能測，不需要身體的資料庫也在跑）。
>
> MVP 階段若後端是單一 FastAPI 服務（同一個 Cloud Run instance），這幾個介面可以先實作成模組間的 Python 函式呼叫；未來要拆成獨立服務時，介面簽章不用大改，直接升級成內部 REST/gRPC 呼叫即可。
